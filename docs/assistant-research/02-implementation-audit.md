# Assistant layer research: implementation audit

Written 2026-09-16. Seven read-only audits of the assistant layer above retrieval, run in two passes against the worktree `.claude/worktrees/assistant-web` on branch `feat/assistant-web-search` at dbf2f44 (#385). Pass one covered four dimensions: system prompt and routing policy (P1 to P10); loop mechanics and safety (LOOP-1 to LOOP-10); provenance and UX (F1 to F10); evaluation and observability (EO-1 to EO-9). Pass two covered three more: conversation, persona, formatting and memory (C1 to C10); permissions, privacy, compliance and guardrails (D1 to D10); feedback, knowledge hygiene, delivery and operations (K1 to K8). 67 findings were raised in total, 39 in pass one and 28 in pass two. Ten from each pass were sent to a skeptic who re-ran every reproduction against the real modules with a fake or stubbed LLM client (no paid call, no network) and re-fetched the vendor pages: all twenty held, twelve at a reduced severity, none refuted. The other 47 are listed unverified at the end.

Code references are file:line under `apps/api/src/assistant/` unless another path is given. Research references such as [R1] are keys into the Sources list of `01-best-practices.md`; the few URLs quoted directly here are repeated at the end. Sizes: S is under half a day, M is one to three days, L is a week-class slice.

### 2. D3, HIGH. The privacy page and ADR-0028 both promise that the web query carries neither the question nor company data, and nothing enforces it

- File: `apps/web/src/routes/privacy-content.ts:88`; `llm-client.ts:97-101`; `answer-service.ts:119`.
- Evidence: the published policy states "the model may run a web search through the same provider; the search engine receives a short query the model writes, not your question or any company document" (:88, Hebrew twin at :186). docs/adr/0028:116-117 repeats it: "Only a short model-written query reaches the engine, never the question or a document, and the privacy page says so." Nothing implements that. WEB_SEARCH_TOOL is `{ engine: 'native', max_results: 3, max_uses: 2 }` with the query written wholly by the model, answer-service.ts:119 offers it on every round and tool-loop.ts:169-172 rebuilds the definitions each round gated only on the search count, never on what the previous round returned. A grep of grounding.ts for "query" returns nothing: the built prompt contains no rule about what a search query may hold. Reproduced with a fake model over an unmodified copy of the loop: round 1 calls people_directory, the tool returns "- Dana Levi (branch_manager, Talpiot, dana.levi@burgers.co.il)", and round 2's request still carries `{ type: 'openrouter:web_search' }` with those names and emails in the same message array. The material at risk is real personal data: tools.ts:431-434 formats each person as name, role, branch and email, tools.ts:493-495 returns full WhatsApp summary text, and apps/whatsapp-digest/src/summary.ts:198 instructs the summariser "Name the people involved when the transcript names them". Nothing can detect a breach either: llm-client.ts:407 reads only `usage.server_tool_use.web_search_requests`, a count, and :417-426 keeps only url and title from the annotations. The vendor pages corroborate both halves: OpenRouter's native engine delegates to "the model provider's built-in web search capabilities" and standardises results to url_citation with no query text [R1] [R2], while Google's grounding "automatically generates one or multiple search queries and executes them" after it "analyzes the prompt" [G1], so the queries are derived from the full conversation context and Google does return them upstream as webSearchQueries, which the broker simply does not pass through.
- Skeptic's verdict: holds, and worse in framing than the auditor put it. The policy sentence is not merely unenforced, it is routinely untrue by construction, because the most likely carrier of company data is the question itself, which is exactly what the sentence denies. Second correction: the MAX_WEB_SEARCHES gate the fix would sit beside is itself soft, since tool-loop.ts:171 counts only what the broker reported and ADR-0028:114-115 records that the native engine reported no server_tool_use in the spike, so a structural gate must key off the trace, which the loop already has in hand at :226, not off the reported count. High: a bilingual published notice plus an ADR assert a third-party-recipient guarantee with zero enforcement and zero detection, and by ADR-0028:116's own line the web leg has no zero-data-retention cover, so anything that rides a query lands in Google's logs under retention nobody here controls.
- Recommendation (S for the prompt and the page, M with the loop gate and test): put the rule in the prompt with a Hebrew twin ("a web search query holds only the public question, a law, a rate, a holiday, a supplier's public page; never a person's name, phone, address, an amount, or any text from a tool result"), and back it structurally by withholding the server tool on any round after people_directory or whatsapp_summaries returned rows, keyed off the trace beside the existing MAX_WEB_SEARCHES gate. Until the query text can be captured, soften the privacy-page sentence to what the app actually guarantees. One loop test asserting the server tool is absent from the round after a people_directory 'ok'.
- Practice failed: egress minimisation on the web leg (01, Lens 6 row 14); lock the processor chain (01, Lens 7 row 3).

### 3. D5, HIGH. The WhatsApp ingestion and its per-person summaries are absent from the privacy page while the assistant serves them to head office

- File: `apps/web/src/routes/privacy-content.ts:52` (Hebrew :150); `tools.ts:446-506`; `apps/whatsapp-digest/src/summary.ts:198`.
- Evidence: "What the app stores" (:52-60, Hebrew :150-158) lists the account, tasks, assistant conversations, the notification device, sessions and "Your activity: the time you last used the app ... It is a single timestamp, not a record of what you did." A grep for whatsapp or ווטסאפ across apps/web/src/routes and apps/web/src/i18n returns nothing in either language, and docs/mobile has none either, although the route is live and ungated (App.tsx:71), is linked from /delete-account, and its own header claims it was "written against apps/api/src/db/schema.ts and the services the API really calls". What is missing from it: whatsapp_messages (schema.ts:722-751) keeps id_message, chat_id, sender_id (:731), sender_name (:735), text_message, caption, file_name and sent_at; whatsapp_summaries (:755-773) keeps a per-group daily summary written by a prompt whose line 198 reads "- Name the people involved when the transcript names them." The assistant is a second reader: tools.ts:446-506 is gated only by readsWhatsappSummaries (:107-108), which 13 of the 18 roles pass, with no capability switch, and it is wired into production at wire.ts:156; whatsapp-summaries.ts:44-60 selects chat_name, summary_date, summary and message_count filtered only by an ILIKE on the group name and a date range, with no branch, location or role predicate. Retention exists only in apps/whatsapp-digest/src/env.ts:109 (messages, 3 days) and :114 (summaries, 10 days) and appears nowhere in "How long it is kept" (:97-103), whose own bullet at :101 says "Assistant threads stay until they are deleted" while messages.content (schema.ts:367) has no TTL, so a summary quoted into a head-office thread outlives both purges. Two gaps beyond the finding as raised: "Who else processes it" (:80-91) never names Green API, the gateway the group traffic actually passes through (apps/whatsapp-digest/src/green-api-client.ts:379, api.green-api.com), and the digest's summarising model is a separate provider setting (env.ts:130) whose purpose the OpenRouter bullet at :88 does not cover. No privacy, notice or consent text exists anywhere in apps/whatsapp-digest or docs/adr/0026.
- Skeptic's verdict: every cited fact reproduced; if anything the finding understates the processor gap. One correction to the legal framing: section 11 of the Protection of Privacy Law, even as expanded by Amendment 13, is worded around "any request to a person to obtain personal data", that is, direct collection, so it is the weakest leg for messages harvested from a gateway; the load-bearing authorities are section 8(b) purpose limitation, which Amendment 13 codified and the PPA first enforced in August 2025 over a database used beyond its declared purpose, and, where GDPR applies (which this very policy invokes at :115), Article 14's indirect-collection notice. That strengthens the recommendation, because a pinned notice in each ingested group is what turns indirect collection into notice at the point of collection. High: this is the document the store listings point at, the omitted category is employee conversation content naming individuals, and the purpose-limitation rule has carried administrative fines since August 2025.
- Recommendation (M): add the channel to both language versions, one "what is stored" bullet (group messages from the chain's WhatsApp groups, including who sent them; a daily AI-written summary per group), the purpose (a branch operations record, not conduct monitoring), who reads it (head-office roles, through the assistant), and the 3 and 10 day retention with the note that a summary quoted into a thread lives as long as that thread. Correct or qualify the "not a record of what you did" sentence. Name Green API under "Who else processes it" and say the summariser makes its own model calls over the transcripts. Separately, write the purpose down before the next client conversation and put a pinned notice in each ingested group.
- Practice failed: a section 11 notice at the point of collection (01, Lens 7 row 1); purpose limitation and the Isakov test for the WhatsApp channel (01, Lens 7 row 2).

### 4. P1, MEDIUM (down from high). Freshness routing is a description, not an instruction: no knowledge-cutoff anchor, no "search before answering", no premise check, no "as of" rule

- File: `grounding.ts:385-392`.
- Evidence: the web line is the only freshness rule in the built prompt: "Anything that changes over time is looked up, never recalled: a VAT rate, a tax or labour rule, a price, a public holiday date, an opening hour, the news. Say which page or which date a web fact comes from." (no-search variant :390-392: "do not fill the gap from memory"). A grep over grounding.ts, tools.ts, llm-client.ts, tool-loop.ts, answer-service.ts and all of apps/api/src finds "cutoff", "training", "as of", "outdated", "premise", "assum", "before answering", "January 2025" nowhere in prompt source. Google's Gemini 3 guide: "Gemini 3 models have a knowledge cutoff of January 2025. For more recent information, use the Search Grounding tool" [G3]; Israel's VAT rose from 17% to 18% on 2025-01-01 [T26] [T27], at that cutoff, which is why the 2026-09-16 battery got 17% from memory (grounding.ts:382-384). WEB_SEARCH_TOOL is model-invoked (llm-client.ts:94-100), so the prompt line is the sole lever. apps/api/test/assistant-prompt.test.ts:62-67 asserts only that "vat" appears and :16-17 says no test pins wording. No post-#385 battery is recorded.
- Skeptic's verdict: every fact reproduces; medium because #385 already routes time-varying facts and names VAT, the gain from imperative over declarative wording is unmeasured and Google asks for short direct lines, so the fix is one or two lines; two corrections, the "as of early 2025, unverified" fallback contradicts the locked no-search policy and a cutoff constant beside defaultModel would drift when prod pins ASSISTANT_MODEL.
- Recommendation (S): add two Rules lines. (1) "Your own knowledge ends around January 2025; today is {today}. Before you answer any public fact that can have changed since then (a rate, a law, a price, a holiday date, an hour, who holds a job), run the web search; when it is not offered, say you could not check and do not give the remembered value as current. When a question assumes such a fact, check the assumption first." (2) "State a changing fact as 'as of <the page's date, or today> according to <site>'." Key the cutoff to the resolved model (llm-client.ts:250) or phrase it generically; add a prompt test for the cutoff string and the imperative; re-run the 10-question battery with the VAT question in Hebrew and English.
- Practice failed: state the date and the model's cutoff (01, Lens 1 row 2); say "look it up, do not guess" in the imperative including premises (01, Lens 1 row 6).

The date-only half (print driveModifiedTime in the heading and the chip, break ties toward the newer document) is S and can ship first.
- Practice failed: document ownership, a verification interval and a visible verified state that feeds retrieval (01, Lens 8 row 6); a freshness SLA per fact class with an "as of" on every answer (01, Lens 10 row 8).

### 9. P2, LOOP-1 and EO-1 (F2 is the same defect, unverified), MEDIUM (all three down from high). Web citations from a tool-calling round are dropped: no chip, and the log records the paid search as empty or not at all

The accurate claim is that it is indistinguishable from a greeting, a refusal or a miss, and the 2026-09-16 bare bubble predates #385, whose web line now routes dated facts to search (unenforced and unmeasured).
5. "Tool descriptions carry no when or when-not, and the web search has no description at all" (P4). Overstated: whatsapp_summaries says "Head-office roles only" (tools.ts:452-453), branch_directory and people_directory carry a "Use it for" sentence, and OpenRouter's server-tool schema has no description field [R1], so the web half is a broker constraint. The "3 to 4 sentences" yardstick is Anthropic's [A6]; Google asks for clear, specific and concise [G2] [G3].
6. "No batching" (P5). Overstated: grounding.ts:435 says "call several when the question spans several" and tool-loop.ts:223 runs a round's calls concurrently. Missing is the "same turn" wording, a lookup count and a stop rule.
7. "When no search is offered, give the remembered value as 'as of early 2025, unverified'" (P1 recommendation). Rejected: it contradicts grounding.ts:390-392 ("do not fill the gap from memory") and ADR-0028's "never an invented fact". The no-search path stays a refusal.
8. "Put the cutoff constant beside defaultModel" (P1 recommendation). Corrected: production can pin ASSISTANT_MODEL (llm-client.ts:147-150, :250), so the constant must be keyed to the resolved model or the line phrased generically.
9. "Set user_location and max_total_results on the native engine" (P3 recommendation). Unproven: OpenRouter documents user_location as native-only, but Google's google_search tool exposes no location or cap parameter [G11] and max_total_results is not documented for native. Set them only after a battery shows an effect.
10. "The branch-hours question ends in 'not found' or a guess" (P4). Unevidenced: the prompt forbids guessing an opening hour (grounding.ts:413) and routes it to the web (:388); no run showed the outcome, and the website mirror will put hours in the knowledge base anyway.
11. "max_uses 2 caps searches at two per answer" (ADR-0028:86-89, the #385 commit body, the comment at llm-client.ts:93-96). Wrong for the live engine: OpenRouter forwards max_uses under native search to Anthropic only and ignores max_results with native [R1]; the loop's own count is the only cap, and the native engine did not report one (P3).
12. "The comment forbids a branch admin in the confidential tier" (D1). Wrong as an intent argument: `git log -L 44,44:apps/api/src/assistant/document-metadata.ts` gives commit 2900f6c, the 18-role expansion itself, whose message reads "confidential adds ceo, chain_manager and finance_manager", so admin was knowingly carried forward while the author was editing that line. The behaviour still needs an owner decision; the comment is not the evidence for it.
13. "The place axis would close the branch-admin lease case" (D1 recommendation). Wrong: every lease pair in corpus-set.json cites one chain-wide dashboard listing Efrat, Big Eilat, Mahane Yehuda and Azrieli Tel Aviv together, so no per-document locationId can scope it to one branch. Only dropping `admin` from the confidential tier, or splitting that dashboard per branch, changes the outcome.
14. "shift_manager is a role whose word form fails the people filter" (C1). Wrong: roleSchema has 18 roles and none is shift_manager. The real failing pairs are chain_chef against "chain chef" and operations_manager against "operations manager", both verified 1 against 0.
15. "The branch number is merely unmatched by the people filter" (C1). Understated: AssistantPersonView has no number field at all, so the number is absent from the haystack, although locations.number exists and branch_directory already prints it as #41.
16. "A fenced code block renders as ``` SELECT 1 ```" (C2). Wrong: the three lines fold to one paragraph and the inline-code pattern then matches the inner backtick pair, so the reader sees two stray backticks, a code span welding the language tag to the statement, and two more backticks. Still garbled, a different string.
17. "Google's Gemini 3 guide says the model emits rich Markdown including tables by default" (C2). Wrong: the page says the opposite ("By default, Gemini 3 is less verbose and prefers providing direct, efficient answers" and a chatty persona "must" be steered explicitly). The table-preference guidance in circulation comes from a leaked Gemini app system instruction, not from API-default behaviour. The finding stands on its code legs without it.
18. "Titles were fixed with a plaintext plus text-start pair" (the repo's own comment at thread-list.tsx:215-222, quoted in C3). Stale relative to its own code: the element is a plain `span dir="auto"` and no `plaintext` utility exists in apps/web/src/index.css. It evidences that the team hit the bidi trap, not that titles are currently fixed that way.
19. "Section 11 of the Protection of Privacy Law is the authority for the WhatsApp ingestion" (D5). Corrected: section 11 is worded around "any request to a person to obtain personal data", that is, direct collection, so it is the weakest leg for messages harvested from a gateway. The load-bearing authorities are section 8(b) purpose limitation and, where GDPR applies (which the policy itself invokes), Article 14's indirect-collection notice.
20. "The `user` field is a data-protection control" (D4). Corrected: OpenRouter documents it as a per-end-user identifier for abuse isolation. The ZDR and data_collection half is the substantive part of that finding.
21. "Gate the provider block to the openrouter preset because the direct endpoints reject the shape" (D4 recommendation). Corrected: embedding-client.ts sends its provider block unconditionally to both base URLs and its own comment says the direct Gemini endpoint ignores it. Gating is still the right conservative choice, for a different reason.
22. "Hang the egress withhold beside the MAX_WEB_SEARCHES gate" (D3 recommendation). Corrected: that gate counts only what the broker reported, and ADR-0028:114-115 records that the native engine reported nothing in the spike, so a structural gate must key off the trace, which the loop already has in hand at tool-loop.ts:226.
23. "An OpenRouter models array covers a retired model id" (K2 recommendation). Unproven: OpenRouter documents its fallback triggers as context-length errors, moderation flags, rate-limiting and downtime [K41], none of which clearly covers a 404 on a retired id. The array hardens the rate-limit and downtime class; the consecutive-unavailable ops alert is what covers the cited precedent.
24. "Cite the SimpleQA abstention figures from the paper PDF with a page number" (the coverage critic's proposed fix to pass one). Wrong: pdftotext over the PDF finds no occurrence of "SimpleQA" and none of 52%, 26%, 1% or 75% in its 1,902 extracted lines. The figures belong to the blog post alone; the paper supports the mechanism ("abstaining is strictly sub-optimal ... IDK-type responses are maximally penalized"), not the table.

- P7, low. No precedence or dates when sources disagree, and "status=out_of_scope, say it is outside what they can view" (grounding.ts:436) contradicts "The web next, for what the company material does not cover" (:408) for an out-of-scope but public fact. - P8, low. extractSources accepts only a bare last line (grounding.ts:325): "**SOURCES:** ...", "מקורות: ...", "- SOURCES: ..." or a closing sentence after the trailer leaks the machine line into the answer and drops the document chips (reproduced). ANSWER_TEMPERATURE 0.2 (llm-client.ts:236, :367) and reasoning max_tokens 256 (:158) on every Gemini 3.1 Pro call, against Google's 1.0 recommendation and OpenRouter's effort mapping. Loop mechanics and safety

- LOOP-2, medium (same defect as P3). max_uses is never reduced to the remainder and with no reported count up to 8 paid searches per answer (tool-loop.ts:171; llm-client.ts:100). S: per-round remainder, count a cited round as a search, log searches offered and reported.
- LOOP-3, medium. The 40 s deadline is a projection gate: a loop ran 76.5 s in an experiment, tool.run has no timeout (tool-loop.ts:174, :223), the client fetch has no signal (apps/web/src/lib/api.ts:112), Fastify runs with default timeouts (apps/api/src/server.ts:290), and the 25 s per-call abort (llm-client.ts:230) can kill a legitimate search round and fold the whole loop to a 503. M: per-call AbortSignal from the remaining deadline, a timeout around tool.run, elapsed per round in the log.
- LOOP-4, medium. No retry for 429, 5xx or AbortError at any round (llm-client.ts:380-382, :404-406, :436-439; tool-loop.ts:181-183); a failed loop returns no usage and logs null tokens (answer-service.ts:174-175); the client re-sends the whole question. M: one jittered retry on a non-final round, re-call with tools withheld on "length", carry partial usage.
- LOOP-5, medium. No progress guard, no per-round fan-out cap, no aggregate result budget (tool-loop.ts:223): an identical search ran 4 times to the cap; 60 people_directory calls in one round pushed about 151k tokens into the next request. - LOOP-6, medium (same defect as P9). Temperature 0.2 and the 256-token reasoning cap on every call with no way to see what the cap does (llm-client.ts:367, :158; reasoning_tokens never read at :317-321). M: preset-and-model scoped parameters, read reasoning_tokens and cached_tokens into the log, re-run the exam and the battery.
- LOOP-7, medium (same defect as P5). A capped answer gets no steering turn and leaves no trace: the model is told to "search again" and then finds its tools gone (tool-loop.ts:207; grounding.ts:435). S: one steering turn, the budget in the prompt, capped and rounds persisted, a localized "partial" line.
- LOOP-8, medium. Tool-result fencing is delimiting only (tool-loop.ts:114): bodies pass verbatim with no source= label, no encoding, the model-written query is echoed (tools.ts:254-256), and apps/api/test has no injection case in either language; mitigated by read-only tools and a link-free renderer. M: source= header, neutralise marker look-alikes or JSON-encode free text, truncate the echoed query, a 30-case Hebrew and English injection suite in CI plus a quarterly run on the real model.
- LOOP-9, medium (same defect as EO-4). Cost per answer is unverifiable: usage.cost, searches, rounds, cap hits and cached and reasoning tokens are dropped (answer-service.ts:215; llm-client.ts:317-321; schema.ts:893-926) and failed loops log null tokens. S: read the fields, add the columns in one migration, fill both row kinds, alert on cost per answer above 3 times the 7-day median.
- LOOP-10, low. Tool arguments are loosely typed (tools.ts:115): a 50,000-character query is embedded and echoed back, a wrong-typed filter is silently dropped into a full listing, days '3', 2.5 and true become the default. S: cap strings at about 300 characters, answer wrong types with status=failed, one unit test per tool.

Feedback, knowledge hygiene, delivery and operations (pass two)

- K3, medium. A person who gets a wrong answer has no way to say so, and no vote is stored anywhere (message-list.tsx:152-175; schema.ts:893-926). A repo-wide grep for feedback, thumb or helpful returns only toast icons, so the one free quality signal is discarded on every answer and the client's operations lead has nothing to read weekly. M: one feedback table keyed to the answer-log id with a typed reason enum and a capped comment, two buttons under each agent turn in both languages, never forwarded to the broker, plus one routing rule sending every downvote to a review queue under a super_admin gate and a 90-day TTL.
- K4, medium. An honest "I did not find it" is logged as a success, so nobody is ever told what the corpus is missing: the status enum is only answered or unavailable (answer-log.ts:16), the miss text search_documents composes is discarded (tools.ts:250-255), no outcome is derived (answer-service.ts:136-221), and knowledge_docs has no owner to route a gap cluster to. M: an outcome column derived from the trace, a 28-day clustering job over the cross-lingual embedding so Hebrew and English phrasings of one gap merge, routing by department, and expiry of an unactioned item after four weeks.
- K5, medium. The paid answer route has no rate limit, no one-in-flight guard and no concurrency gate; the only spend guard is an hourly balance poll (routes/threads.ts:201; app.ts:80-124; credit-guard.ts:12). @fastify/rate-limit is not a dependency and the repo's single limiter is the password-reset window. At ADR-0028's own 1.4 to 3 cents an answer, roughly 20 concurrent 20-second loops is about 3,600 answers an hour, which can empty the account inside one poll interval. S to M: a per-user window (20 per 10 minutes plus a soft 150 a day), one running answer per user, a process-wide gate of about six loops using the shape chunk-index.ts:83-96 already has, and `user: sha256(userId)` on every broker call.
- K6, medium. A retry after a dropped connection buys the same answer twice and leaves a duplicate exchange in the thread (assistant-screen.tsx:166-177; answer-service.ts:200-207; packages/shared/src/index.ts:1188-1190). The catch comment's premise ("Nothing was persisted, so retry re-asks in place") holds for the 503 path and not for the transport path, and the request body carries only content so the server cannot tell the two apart; the window is the full 40-second deadline plus the final call. S to M: a clientMessageId with a unique index on (thread_id, client_message_id) and three server outcomes; until then, refetch the thread before offering retry.
- K7, medium. Every deploy kills answers in flight: npm is PID 1, no SIGTERM handler exists anywhere in apps/api/src so the onClose hook never runs, docker-compose.prod.yml sets no stop_grace_period against Docker's 10-second default, and deploy-vps.sh:50 recreates the container before waiting on health. S: a SIGTERM handler calling app.close() with a preClose that refuses new questions, node as PID 1, stop_grace_period 90s, and a drain wait in the deploy script.
- K8, low. The health check and the deploy gate read healthy straight through an assistant outage, and the client has no status to read before it makes someone wait (routes/health.ts:36-64; credit-guard.ts:48; assistant-screen.tsx:140-170). S: an `assistant:availability` check computed from the answer log with no model call, kept out of the container-level status so Docker never restarts the API because Google is slow, exposed to the SPA with a short cache and a muted bilingual line.
